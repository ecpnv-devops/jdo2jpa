# Draft GitHub Release Notes

## Correct dependent relationship lifecycle translation

JDO dependency metadata now controls both parent-delete cascading and disassociation-time orphan removal for relationship mappings generated by `ReplacePersistentWithOneToManyAnnotation`.

### Corrected orphan-removal derivation

Dependent relationships now receive both `CascadeType.REMOVE` and `orphanRemoval = true`.
Non-dependent relationships no longer receive `orphanRemoval = true` merely because their inverse foreign key is mandatory.
This restores JDO lifecycle semantics and avoids inferring ownership from database optionality.

Consumers can find affected mappings by reviewing collections declared with `@Persistent(dependentElement = "true")` whose inverse reference is optional, because those mappings now delete children removed from the collection.
Consumers should also review collections declared with `@Persistent(mappedBy = ...)` without dependency metadata whose inverse reference is mandatory, because those mappings no longer delete removed children implicitly.

### Recognise dependency declared with `@Element`

Collection dependency declared through `@Element(dependent = "true")` is now recognised even when `@Persistent` is also present.
For collections, `@Element(dependent)` takes precedence over `@Persistent(dependentElement)` when both are explicitly supplied.
This correction may add `CascadeType.REMOVE` and `orphanRemoval = true` when a previous regeneration missed the element-level declaration.

### Support dependent generated `@OneToOne` mappings

Single-valued relationships converted to `@OneToOne` now map `@Persistent(dependent = "true")` to both `CascadeType.REMOVE` and `orphanRemoval = true`.
The legacy `dependentElement` spelling remains accepted as a fallback for these relationships.

### `@ManyToOne` limitation and consumer handoff

Dependent references translated to `@ManyToOne` continue to receive `CascadeType.REMOVE`, but JPA does not provide an orphan-removal attribute for `@ManyToOne`.
The recipe does not generate mutators, callbacks, or listeners to delete a displaced referent.
Consumers that reassign dependent many-to-one references must enforce the required lifecycle behavior in application code and regression tests.
Estatio should own follow-up coverage for `CodaTransactionFetchOrchestration.codaTransaction` and cross-ORM disassociation, re-parenting, and parent-deletion scenarios for the affected collections.
