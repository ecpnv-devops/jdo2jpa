## Why

`ReplacePersistentWithOneToManyAnnotation` derives `CascadeType.REMOVE` from JDO dependency metadata, but derives `orphanRemoval` from an unrelated signal: whether the inverse (`mappedBy`) field is mandatory.
Foreign-key optionality and dependency ownership are different facts, so the generated mapping diverges from JDO in both directions — collections JDO deleted are retained, and collections JDO retained are deleted.

JDO dependency deletes a child both when the parent is deleted *and* when the child leaves the relationship.
JPA needs two annotations to express that: `CascadeType.REMOVE` for the first and `orphanRemoval = true` for the second.
Emitting only the first silently drops half the contract.

In the Estatio consumer this affects seven collection mappings, five of which expose `removeFrom…` methods, so the difference is executable domain behaviour rather than metadata drift.

## What Changes

- Derive `orphanRemoval = true` from the same JDO dependency metadata that already drives `CascadeType.REMOVE`, for both mapping shapes this recipe generates.
- Stop inferring orphan removal from a mandatory inverse foreign key, and remove the now-unused accumulator plumbing that supports that inference.
- Resolve dependency in a cardinality-aware way, because JDO spells the flag differently for collections and single references, and this recipe generates both.
- Treat an explicit `false` as non-dependent, emitting neither `CascadeType.REMOVE` nor `orphanRemoval`.
- Add recipe fixtures covering the cross-product of dependency metadata, mapping shape, and inverse-field optionality.

## Capabilities

### New Capabilities

- `dependent-collection-lifecycle`: Defines how JDO dependency metadata is translated into JPA cascade and orphan-removal semantics for the relationship shapes this recipe generates, and what must not be inferred from unrelated mapping facts.

### Modified Capabilities

None.

## Impact

Generated mappings change for two populations.
Dependent relationships whose inverse field is optional gain `orphanRemoval = true`; non-dependent relationships whose inverse field is mandatory lose it.
Both are behavioural changes in consuming applications, not metadata-only edits, so consumers must regenerate and exercise their disassociation paths.

Measured against Estatio: seven `@OneToMany` mappings change (five gain, two lose). No generated `@OneToOne` changes, because Estatio declares no dependent single-valued `@Persistent`. No mapping changes through the `@Element` dependency spelling, because Estatio does not use it.

No database schema changes; no runtime dependency; no ORM conditional is introduced.

## Out of scope

- **`@ManyToOne` disassociation semantics.** `ReplacePersistentWithManyToOneAnnotation` emits `CascadeType.REMOVE` for a dependent single reference, and that is the whole of what a `@ManyToOne` can express — JPA offers no `orphanRemoval` there. Note this limitation applies *only* to `@ManyToOne`; the `@OneToOne` mappings generated by this recipe can and now do express it.
- **Consumer regression tests.** Cross-ORM disassociation, re-parenting and parent-deletion tests over the seven Estatio collections belong in that repository, which has both ORMs available. This change supplies recipe fixtures only.

Both are currently **untracked**: Estatio's `openspec/planned-changes/` was emptied when these proposals moved here, so no change owns the consumer-side work.
A change should be raised in Estatio covering the `@ManyToOne` case (`CodaTransactionFetchOrchestration.codaTransaction`, whose field is assigned only in its two constructors, so an architecture rule asserting no reassignment path may be sufficient) and the cross-ORM tests.
Raising it is a **handoff, not an acceptance criterion** for this change — a library release cannot be gated on a consumer repository.
